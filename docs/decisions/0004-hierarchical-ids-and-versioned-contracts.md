# ADR-0004: 使用分层对象 ID 与版本化跨语言 contract

## Status

Accepted

## Date

2026-08-06

## Context

MVP 只覆盖太阳系，但产品定位允许未来增加卫星、表面站点、拉格朗日点、其他恒星系统和更大尺度的导航。若以名称、数组位置或仅在太阳系内唯一的短 ID 关联对象，扩展后会产生冲突，并迫使路线、收藏、离线包和缓存迁移。

Flutter 与 Rust 还需要在独立发布节奏下识别数据结构与目录内容是否兼容。

## Decision

每个对象使用稳定、分层、全目录唯一的字符串 ID，例如：

```text
sol/sun
sol/earth
sol/earth/moon
sol/earth/moon/artemis-base
```

每个对象同时包含：

- `systemId`：当前为 `sol`，未来一个恒星系统或独立数据域使用新的 ID；
- `parentId`：表达对象层级，可空根节点；
- `orbit.parentId`：表达教学轨道的参考中心；
- `orbit.provenance`：表达整组教学轨道参数的性质、来源与近似限制。

父引用必须存在、不能成环、不能跨系统。有轨道参数的对象必须使用 `orbit.parentId` 作为坐标参考中心，不能用对象层级 `parentId` 覆盖；没有轨道参数的表面设施可以依附层级父对象生成明确标注性质的地图示意位置。显示名称可以变化，稳定 ID 不随中文或英文品牌变化。

目录与 bridge 分别版本化：

- `catalogVersion` 标识具体数据快照和模型输入；
- `schemaVersion` 标识 JSON 结构兼容性；
- 时间相关 envelope 附带 `dayFromJ2000`；
- 离线包 manifest 独立包含 schema、pack ID、system ID、缩放范围和校验和。

当前渲染器只消费 `sol`。未来深空能力通过新增 system catalog、尺度适配器和路线域实现，不把光年尺度坐标直接塞进当前 AU 画布。

## Alternatives Considered

### 使用自增整数 ID

- 优点：紧凑、索引方便；
- 缺点：离线合并、跨系统导入和人工审查时缺少稳定语义；
- 结论：拒绝，字符串路径更适合版本化科学目录。

### 只使用对象英文名

- 优点：可读；
- 缺点：重名、别名和命名更新会破坏引用；
- 结论：名称仅用于展示和搜索。

### 建立一套跨宇宙的统一笛卡尔坐标

- 优点：表面上只有一个渲染模型；
- 缺点：太阳系、恒星和星系尺度差异巨大，精度、LOD 和交互语义不同；
- 结论：使用系统域和未来尺度适配器。

### 只给 App 版本，不给 catalog / schema 版本

- 优点：版本字段更少；
- 缺点：无法判断相同 App 下的数据快照或 bridge 结构是否兼容；
- 结论：分别版本化。

## Consequences

- 现有路线、缓存和测试可依赖稳定 ID；
- 可以新增其他系统而不重命名 `sol/...` 对象；
- 导入工具必须检查唯一性、父引用、循环和系统命名空间；
- schema 不兼容变化必须提升版本并提供迁移；
- 当前只算预留了深空 contract，并不代表已实现跨星际导航。
